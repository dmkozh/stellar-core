## Meta-Patterns

1. **Benchmark workload invalidates the premise**: Multiple hypotheses assumed worst-case conditions that simply do not exist in the benchmark (005: all probes hit; 008: all RW entries mutated; 009: Soroban keys never prefetched; 022: only one parallel phase). Always verify the actual benchmark workload shape before building an efficiency argument.

2. **Prefetching absorbs serial lookup overhead**: `prefetchTransactionData` and `prefetchTxSourceIds` load relevant entries into the root cache before any transaction processing. This makes subsequent per-entry lookups fast enough that optimizations targeting individual load calls (001, 023) are not viable unless profiling confirms cache miss rates >50%.

3. **Cache-overhead exceeds cache-savings**: Three PoCs (010, 012, 021) passed all tests but were rejected after independent benchmarking revealed flat-to-negative results. Adding `unordered_map` memoization or contiguous buffer batching introduced overhead (key hashing, map management, allocations) that equaled or exceeded the eliminated work. Always benchmark cache additions against the baseline before claiming a win.

4. **LedgerTxn architectural hard limits**: The `LedgerTxn` subsystem enforces single-active-child and thread-affinity constraints by design. Any hypothesis that requires concurrent child `LedgerTxn` operations on the same parent (024) or that tries to route around the transaction hierarchy (023) must account for these constraints, which typically require rewriting the full validation stack.

5. **Incorrectly guarding invariants off config**: Using `config.INVARIANT_CHECKS.empty()` as a guard for invariant-path skipping is unsafe because invariants can be enabled programmatically after startup. Any optimization that conditionally skips invariant-related work must key off the invariant manager's live enabled set, not the static config.

6. **Bridge shape changes have disproportionate implementation cost**: Changing `InvokeHostFunctionOutput` or other CXX bridge structs requires coordinated changes to the Rust bridge definition, Rust extraction functions, and C++ processing code. This is justified only when the targeted XDR payloads are large or variable-size. For fixed-size small entries (TTL ≈ 48 bytes, cost params ≈ 1.7kB), the implementation cost far exceeds measurable savings (016, 018, 021).

7. **Near-duplicate of confirmed success**: When a success has already landed for a code path (e.g., `soroban-env/001` covering cost-param XDR round-trips), hypotheses targeting the same path but at a marginally different layer (017) rarely find meaningful additional headroom. Always cross-check all `success/` directories for the targeted source files.

8. **TTL overhead is small in aggregate**: Multiple angles on TTL-related overhead (010, 013, 018, 019, 020) converge on the same conclusion: per-call TTL costs (SHA256, materialization, container building, or XDR encode/decode) are each 50–700ns, total TTL processing per ledger is <5ms, and these costs are distributed across worker threads. No single TTL micro-optimization reaches the 5% Low threshold independently.
